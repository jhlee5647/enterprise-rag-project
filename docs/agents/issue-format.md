# 이슈·PR 본문 형식

`/to-spec`, `/to-tickets`, `/pr`로 이슈나 PR 본문을 쓸 때 이 문서의 형식을 따른다. 스킬에 들어 있는 템플릿과 다르면 이 문서가 우선한다. 각 스킬의 나머지 절차(seam 확인, 티켓 분할 확인, 라벨, 차단 관계 등)는 그대로 따른다.

본문은 한국어로 쓴다. 명령어, 코드, 라벨 문자열은 원문 그대로 둔다.

## 공통 원칙

- **한 사실은 한 곳에만 쓴다.** 결정의 근거는 ADR이나 설계 기록에 두고, 이슈와 PR에서는 링크로 가리킨다. 스펙 내용은 스펙 이슈에, 테스트 사례는 티켓에, 통과 여부는 PR에 둔다.
- 결정을 담은 값(기간, 경계값, 모델명, 기대 숫자)은 구체적으로 쓴다. 구현 중 바뀌기 쉬운 값(파일 경로, 함수 이름, CLI 플래그 문자열, 코드 스니펫)은 동작으로 설명한다. 사용자가 실행하는 명령 이름처럼 seam 자체인 것은 이름까지 쓴다.
- 프로토타입에서 나온 스니펫이 결정을 글보다 정확히 담으면, 핵심 부분만 인라인으로 넣고 프로토타입 출처를 밝힌다.

## 스펙 이슈 (`/to-spec`)

제목: `[Epic] <기능 이름>`

독자는 리뷰어(사람)와 에이전트다. 본문을 두 부분으로 나눈다.

- **For Agents가 기준이다.** 스펙의 모든 요구사항과 결정은 For Agents에 있다.
- **For Humans는 For Agents의 요약이다.** For Agents에 있는 내용만 골라 짧게 쓴다. 스펙을 고칠 때는 For Agents를 먼저 고치고 For Humans를 맞춘다.

```markdown
# For Humans

> **이 섹션에 대해**: 이 이슈의 독자는 둘이다. 구현 에이전트는 다른 맥락 없이 이 이슈만 보고 작업하므로, 요구사항·결정·테스트 기준이 빠짐없이 적힌 For Agents가 필요하다. 그 결과 For Agents는 길고 세밀해서, 사람(리뷰어·이해관계자)이 무엇을 왜 만들고 무엇을 결정했는지 빠르게 파악하기 어렵다. For Humans는 사람 독자가 방향과 핵심 결정을 검토할 수 있도록 For Agents를 추린 요약이다. 새 내용은 없으며, 둘이 다르면 For Agents가 기준이다. 스펙을 고칠 때는 For Agents를 먼저 고치고 이 섹션을 맞춘다.

## 개요
네 항목을 각 1~2줄로 쓴다.
- **상황**: 어떤 데이터나 현업 상황을 상정했는지.
- **문제**: 사용자가 겪는 문제와, 해결책이 지켜야 할 조건.
- **선택**: 검토한 대안과 고른 방식, 고른 핵심 이유.
- **단계**: 이번 스펙이 집중하는 것과 이후 계획. "~는 목표가 아니다" 같은 부정형 대신 "이번에는 A에 집중하고, B는 다음 단계에서 한다"로 쓴다.

## 이번 개발 범위
주요 산출물(축)마다 한 줄씩 번호 목록으로 쓴다. 여러 축에 걸쳐 지켜야 하는 요구사항(예: 권한, 개인정보)이 있으면 목록 아래에 따로 적고, 어떻게 확인하는지도 함께 쓴다.

## 주요 결정 사항
- 핵심 결정 3~5개. 각 결정은 ADR이나 설계 기록 링크로 연결한다.
- 나머지 결정은 설계 기록 링크 하나로 가리킨다.

## 다음 개발 범위
이 스펙 다음에 이어질 작업. 1~2줄.

# For Agents

## Problem Statement
## Solution
## User Stories
## Implementation Decisions
## Testing Decisions
## Out of Scope
## Further Notes
```

For Agents 각 섹션은 `/to-spec` 템플릿의 설명대로 쓴다. 특히 다음을 지킨다.

- **Problem Statement**: 상정한 데이터나 현업 상황을 먼저 쓴다. 이번 단계의 초점과 이후 계획도 여기에 쓴다.
- **Solution**: 대안을 비교해 방식을 골랐다면, 후보별 탈락·선택 이유를 맨 앞에 짧게 쓰고 ADR로 연결한다.
- **User Stories**: "<행위자>로서, <기능>을 원한다. <이점>을 위해." 형식의 번호 목록을 기능의 모든 측면을 덮을 만큼 길게 쓴다. `/to-tickets`는 이 목록으로 티켓을 나누고, `/code-review`의 Spec 검토는 이 목록으로 빠진 요구사항을 찾는다.
- **Testing Decisions**: 테스트 seam과 그 seam을 고른 이유를 쓴다. DB나 파일 같은 저장 결과를 직접 조회해 검증한다면, 그 저장 결과가 다른 단계와의 공식 계약(공개 인터페이스)이라는 근거를 함께 쓴다.

## 구현 티켓 (`/to-tickets`)

독자는 구현하는 에이전트와 리뷰어다. `/implement`는 티켓 하나만 보고 새 컨텍스트에서 시작하므로, 티켓만 읽고 구현할 수 있게 쓴다. 이 프로젝트를 처음 보는 개발자도 막힘없이 읽을 수 있어야 한다.

```markdown
## Parent
#<스펙 이슈 번호>

## 용어
이 티켓을 읽는 데 필요한 말. 도메인 용어의 정식 정의는 GLOSSARY.md로 연결한다.

| 용어 | 설명 |
|---|---|
| ... | 한두 문장. 무엇인지와 이 티켓에서 어떻게 쓰이는지. |

## What to build
- 이 티켓이 동작하게 만드는 end-to-end 행동. 사용자 관점으로 쓴다.
- 이 결과를 이어받는 이후 티켓.
- 범위 밖: 다른 티켓이 맡는 것 (티켓 번호와 함께).

## 결정 근거
- 표의 링크는 설계 기록이나 ADR의 해당 절로 이동한다.

**근거가 기록된 결정**

| 결정 | 근거 | 기록 |
|---|---|---|

**대안 비교 없이 정한 기본값**
- 대안을 따로 비교하지 않고 가장 단순하고 일반적인 방식으로 정한 결정. 문제가 드러나면 다시 검토한다.

| 결정 | 기록 |
|---|---|

## Data flow
(선택) 입력 데이터의 형태와 처리 순서. 처리 순서의 각 단계에 담당 모듈을 **[모듈 이름]**으로 표시한다.

## Acceptance criteria

### 테스트 방법
- 아래 표의 사례는 모두 자동 테스트로 검증되어야 한다. 이 사례가 모두 검증되면 티켓이 완료된다.
- 표는 검증할 **사례 목록**이다. 테스트의 개수와 묶음, 진행 순서는 `/tdd`의 red → green 사이클을 돌면서 정한다. 사례 하나를 여러 테스트로 나누거나 여러 사례를 한 테스트로 묶어도 된다.
- 테스트 seam: <어디서 실행하고 무엇을 조회해 확인하는지>.
- 구현 중 필요해진 사례는 PR의 "티켓과 달라진 점"에 적는다.

| 번호 | 종류 | 상황·입력 | 기대 결과 | 필요한 이유 |
|---|---|---|---|---|
| T1 | 정상 / 경계 / 실패 | ... | ... | ... |

### 그 밖의 완료 조건 (자동 테스트 아님)

| 항목 | 확인 방법 |
|---|---|

### 가정 (스펙에 없던 동작)
- 스펙에 없지만 이 티켓에서 정한 동작. 관련 사례 번호를 함께 쓴다.

## Blocked by
- #<번호>, 또는 "None (can start immediately)". GitHub 기본 의존성으로 연결했으면 이 섹션을 생략한다.
```

- **용어 절에는 처음 보는 개발자가 막힐 만한 말을 모두 넣는다.** 도메인 용어, 외부 시스템(예: Solr, S3), 약어, 파일 형식(예: parquet), 설정 항목 이름, 테스트 용어(예: fixture)가 대상이다. 다른 티켓에서 이미 설명한 용어는 "#<번호>의 용어 절 참고"로 가리킨다. 본문에서 처음 쓰는 말이 용어 절에 없으면 추가한다.
- 업계 용어를 직역한 표현(예: "녹화된 응답")은 쓰지 않고, 무엇인지 드러나는 말("저장된 응답 fixture")로 쓴다.
- **기대 결과는 독립적인 값으로 쓴다.** 구체적인 숫자, 날짜, 문자열로 적어서 코드와 같은 계산으로 기대값을 만드는 테스트가 나오지 않게 한다.
- 경계값은 양쪽(바로 안과 바로 밖)을 모두 사례로 넣는다.
- 통과 여부(✅)는 티켓에 적지 않는다. PR에서 관리한다.

## PR (`/pr`)

제목: `<feat|fix|...>: <사용자 관점의 변경 한 줄> (#<티켓 번호>)`

독자는 리뷰어다. **리뷰어는 티켓을 읽은 상태**로 본다. 결정과 사례 설명은 티켓에 있으므로, PR에는 **만든 것, 티켓과 달라진 점, 검증 결과**만 쓴다. 구현 중에 알게 된 것(외부 시스템의 실제 동작, 실제 데이터의 모양, 리뷰 반영 사항)은 리뷰어가 모르는 것으로 보고 쓴다.

```markdown
> **읽기 전에**: [티켓 #<티켓 번호> <티켓 제목>](<티켓 URL>)을 읽은 리뷰어를 기준으로 씀. 결정의 근거와 테스트 사례 설명은 티켓에 있으므로 반복하지 않음. 이 PR에는 만든 것, 구현 중 티켓과 달라진 점, 검증 결과만 적음.

## 요약

### 주요 기능
<이 PR이 동작하게 만든 것 한 줄>

**Input**
- <입력과 그 안의 주요 값>

**Logic**
1. <처리 단계를 순서대로, 한 단계에 한 줄>

**Output**
| 출력 | 내용 | 누가 쓰나 |
|---|---|---|

<결과물의 실제 예시(표 한 행, 출력 몇 줄 등)>

### 함께 만든 것
- 뼈대, 도구, 문서 등 부수적인 변경

### 주요 변경 파일
| 파일 | 내용 |
|---|---|

## 티켓과 달라진 점
- 추가한 산출물, 외부 시스템에 맞춰 바꾼 것, 티켓에 없어서 정한 것, 추가한 테스트 사례, 범위 조정. 중요한 것부터 묶어 쓴다. 없으면 "없음".

## 검증
티켓 [#<티켓 번호>의 Acceptance criteria](<티켓 URL>#acceptance-criteria) 사례는 테스트 이름의 번호(`tNN`)로 연결함.

<명령과 그 출력. 전체 테스트(`pytest -v`), 필요하면 실제 실행 결과>

그 밖의 완료 조건: <항목과 확인 결과>

## Merge Danger
**Door:** one-way / two-way
<되돌리기 어려운 부분이 있으면 설명>

**Blast Radius:** <한 단어>
<병합 시 영향을 받는 범위>

Closes #<티켓 번호>
```

- 주요 기능은 Input / Logic / Output 형태로 쓴다. 도식(Mermaid 등)이나 처리 순서를 압축한 의사코드, 쿼리 문법은 쓰지 않는다. Logic은 번호 목록으로 순서대로 풀어 쓴다.
- 요약은 주요 기능을 먼저 쓰고, 뼈대·도구·문서 같은 부수적인 변경은 뒤에 쓴다.
- 검증에는 명령과 출력만 둔다. 사례 설명은 티켓 링크로 대신한다. 사례별 통과 여부는 테스트 이름의 사례 번호로 출력에서 보이게 한다(예: `test_t02_...`, 여러 사례를 묶으면 `test_t04_t05_...`, 티켓에 없던 사례는 `test_extra_...`). 구현 전 실패(red) 기록은 커밋 이력에 맡기고 PR에는 쓰지 않는다.
- 말투는 개조식(~함, ~임, ~음)으로 통일한다.
- **티켓 본문은 고치지 않는다.** 티켓은 합의한 계획의 기록으로 둔다. PR을 만든 뒤 티켓에 "구현 중 달라진 점은 PR #<번호>의 '티켓과 달라진 점' 참고" 댓글을 단다. 이후 단계가 기대는 사실(용어, 계약)은 `GLOSSARY.md`나 ADR에 반영한다.
