# 검색 정확도·지연 시간 개선 설계 기록

#17 에픽(마스킹 품질·색인 속도·평가 신뢰도)을 마친 뒤, 검색 정확도와 지연 시간을 개선하는 에픽의 측정과 결정을 모은다. 결정의 근거는 여기에 두고, 스펙 이슈와 티켓은 이 문서의 절을 가리킨다.

## 0. 측정 조건

- 데이터: 표본 9,000건, 청크 512 / 겹침 64(청크 70,398개), 마스커는 이름 찾기 모델 `gliner`(#44, #46).
- 색인: Pod 안 Qdrant 서버의 `chunks` 컬렉션. 임베딩 `Qwen/Qwen3-Embedding-0.6B`(bf16), 거리 cosine, HNSW 기본값(`m` 16, `ef_construct` 100). payload 색인은 없다.
- 평가셋: 출발점 평가셋(#15, 32B로 만든 `keep` O 50문항). 질문마다 부서 3개로 실행해 150번, 그중 권한이 있는 실행 74번.
- 답변 LLM: vLLM의 `Qwen/Qwen3-8B`, `top_k` 5, ACL 필터 켬.
- 환경: RunPod A40 48GB(vLLM과 함께 씀), CPU 한도 7.65코어.

| 지표 | 값 | 실행 |
|---|---|---|
| 검색 적중률 | 0.595 | `runs/gliner-default-44` |
| 거부 정확도 | 0.711 | 같음 |
| 검색 누출률 | 0.0 | 같음 |
| `eval` 전체 시간 | 554초 (실행당 약 3.7초, 모델 불러오기 포함) | 같음 |
| 질문 한 번의 단계별 지연 시간 | 잰 적 없음 | |

이 표는 에픽을 시작할 때의 조건이다. 평가셋을 고친 뒤의 출발점 값은 5.3절에 있다.

## 1. 근사 검색이 상위 5개를 바꾼다

같은 질문 150번을 같은 색인에서 세 가지 방식으로 다시 검색했다.

| 검색 방식 | 검색 적중률 | 상위 5개가 정확한 검색과 다른 실행 |
|---|---|---|
| 지금(HNSW, 기본 탐색 폭) | 0.595 | 31 / 150 |
| HNSW, 탐색 폭 `hnsw_ef` 512 | 0.608 | 확인 안 함 |
| 정확한 최근접 검색 | 0.622 | 0 |

- 지금 방식으로 다시 검색한 결과는 `eval` 기록과 150번 모두 같다. 질문 임베딩과 검색은 같은 색인에서 결정적이다.
- 같은 마스킹 결과로 두 번 만든 색인(`chunks_gliner`, `chunks`)의 검색 적중률이 0.608과 0.595로 달랐다. HNSW 그래프는 만들 때마다 달라지므로, 이 차이도 근사 검색 탓으로 본다.
- 원인 후보: 검색 전에 부서로 거르는데(ACL 필터) 허용 부서 필드에 payload 색인이 없다. Qdrant는 필터를 건 검색에서 HNSW 그래프의 연결이 끊긴 쪽을 놓칠 수 있고, payload 색인이 있어야 필터에 맞춘 그래프 연결을 만든다.

## 3. 지연 시간을 먼저 잰다

지연 시간을 개선하려면 어느 단계가 오래 걸리는지 알아야 하는데, 지금은 `eval` 전체 시간만 있다. 그래서 실행마다 단계별 시간(질문 임베딩, 검색, 답변 생성, 전체)을 남기고, 지표 JSON에 단계별 중앙값과 p95를 남긴다.

- 모델을 불러오는 시간은 질문 한 번의 지연 시간이 아니므로 뺀다. 첫 실행 전에 임베딩 모델을 미리 불러 둔다.
- 개선 방향(답변 길이, vLLM 설정 등)은 이 측정을 보고 다음 단계에서 정한다.

## 4. 근사 검색 고치기

| 후보 | 판단 |
|---|---|
| 허용 부서 필드에 payload 색인 | 먼저 시도. 필터를 건 검색의 표준 설정이고, 청크가 늘어도 근사 검색의 속도를 유지한다. 시도 결과 고쳐지지 않아 정확한 검색으로 바꿨다(4.1) |
| 정확한 최근접 검색으로 바꾸기 | 7만 청크에서는 쓸 만하지만 청크 수에 비례해 느려진다. payload 색인으로도 정확한 검색과 결과가 다르면 이것으로 바꾼다 |
| 탐색 폭(`hnsw_ef`) 늘리기 | 0.608로 정확한 검색(0.622)에 못 미쳤다. 원인(필터)을 고치지 않는다 |

확인: 실제 환경에서 150번의 상위 5개가 정확한 검색과 같은지 본다. 자동 테스트의 Qdrant 로컬 모드는 근사 검색을 하지 않아 이 문제가 나타나지 않는다.

### 4.1 결과 (#49)

| 상태 | 상위 5개가 정확한 검색과 다른 실행 |
|---|---|
| payload 색인 없음 | 31 / 150 |
| 이미 있는 컬렉션에 payload 색인을 더함 | 33 / 150 |
| 같은 색인, 부서 필터 없이 검색 | 9 / 150 |
| 정확한 최근접 검색으로 바꿈 | 0 / 150 (정의상 같음) |

- payload 색인을 더해도 고쳐지지 않았다. 필터 없이도 9번이 달라, 근사 검색 자체가 결과를 놓친다. 그래서 검색을 정확한 최근접 검색으로 바꿨다. payload 색인은 새 색인에 계속 만든다(정확한 검색에서 부서로 거를 때도 쓰인다).
- 정확한 검색으로 바꾼 `eval`(`runs/exact-49`): 검색 적중률 0.595 → 0.622, 검색 단계 중앙값 119ms → 71ms, p95 134ms → 81ms. 7만 청크에서는 정확한 검색이 더 빨랐다. 검색 누출률 0.0, PII 누락률·오탐률 0.076 / 0.125는 그대로다.
- 거부 정확도는 0.711 → 0.684. 검색된 청크가 바뀌면 답변 LLM의 출력도 바뀐다. #24의 마스킹 끔 실행도 0.684였다.

## 5. 평가셋 고치기

### 5.1 다른 판본도 정답으로 인정한다

| 후보 | 판단 |
|---|---|
| 사본 기준을 비슷한 문서까지 넓힘 | #17에서 미룬 것과 같다. 비슷함의 임계값을 정할 근거가 없다 |
| 평가셋에 정답 문서의 다른 판본을 사람이 확인해 적음 | 선택. 판정에서 확인된 문서만 더하므로 근거가 분명하다 |
| 빈틈 실행을 평가셋에서 뺌 | 질문 자체는 좋은 질문이라 버릴 이유가 없다 |

- 다른 판본은 사본처럼 다룬다. 검색되면 적중이고, 실행한 부서가 그 판본의 허용 부서에 있으면 권한이 있다.
- 한계: 판본 목록은 지금 검색 방식(dense)이 찾은 문서에서 나왔다. 다른 검색 방식은 목록에 없는 판본을 찾아도 적중으로 세지 않는다. 새 방식의 실패도 같은 판정으로 확인하고 목록을 보탠다.

### 5.2 모호한 질문은 뺀다

모호로 판정한 질문 2개(실행 3번)는 `keep`을 X로 바꾼다. 질문을 고쳐 다시 쓰면 새 정답 문서를 다시 검수해야 하므로, 이번에는 빼기만 한다.

평가셋을 고친 뒤 같은 조건으로 출발점 값을 다시 잰다. 이후 비교는 그 값과 한다.

## 6. 하이브리드 검색

실패의 절반 이상이 고유명·약어였다. 질문 임베딩은 드문 단어의 철자를 잘 살리지 못하므로, 단어가 그대로 겹치는지 보는 검색을 섞는다. 의미로 찾아야 하는 질문은 dense가, 고유명이 핵심인 질문은 BM25가 맡는다.

고유명·약어 실패 9번에서 정답 문서가 정확한 검색으로 몇 위였는지(판정 데이터, 부서 필터 적용):

| 질문의 고유명 | 정답 문서 순위 |
|---|---|
| Jezebel | 15 |
| Sacrificial Concepts (2번) | 14, 20 |
| Brand Cling | 46 |
| REG (3번) | 77, 71, 77 |
| The Cannabist | 210 |
| Tobacco 21 National Advocacy | 1,000위 밖 |

9번 중 3번은 후보 20개 안에 들어 리랭커로도 고칠 수 있지만, 6번은 후보에 들지 못해 순서를 바꾸는 것만으로는 못 찾는다. 사례는 질문 6개로 적고, BM25가 실제로 정답 문서를 올릴지는 #53에서 잰다.

| 후보 | 판단 |
|---|---|
| dense + BM25, 순위로 합침(RRF) | 선택. 점수 크기를 맞출 필요가 없고 Qdrant가 서버에서 합친다 |
| dense + BM25, 점수 가중합 | 가중치를 정할 근거가 없다 |
| 리랭커 | 상위 후보 안에 정답이 없으면 순서만 바꿔서는 못 찾는다. 고유명 실패 9번 중 6번은 후보 20개에 들지도 못했다(위 표). 다음 단계에서 본다 |

- BM25는 Qdrant의 sparse 벡터로 같은 컬렉션에 둔다. 단어 가중치는 Pod 안에서 계산한다(ADR-0002).
- 검색 방식은 config로 고른다(`dense`, `hybrid`). 기본값은 `dense`로 두고, 측정 결과를 보고 사람이 바꿀지 정한다(6.1에서 `hybrid`로 바꿈).
- 하이브리드 검색도 ACL 필터를 두 검색 모두에 건다.

같은 색인에서 쟀다. 색인은 sparse 벡터를 더한 형식으로 다시 만들었고, 저장된 마스킹 결과를 다시 써서 마스킹 없이 20.4분 걸렸다. 위 세 줄은 #51의 평가셋, 아래 두 줄은 판정 뒤 다른 판본을 더한 평가셋이다.

| `hybrid`, Qdrant RRF (`hybrid-53`) | 0.784 | 0.575 | 다시 검색하면 144번 중 34번의 상위 5개가 다름(RRF 동점) |

| 판정 뒤 평가셋 보강: `dense` (`dense-53c`) | 0.761 | 0.699 | |
| 판정 뒤 평가셋 보강: `hybrid` (`hybrid-53c`) | **0.854** | **0.603** | 다섯 실행 모두 검색 누출률 0.0 |

- **판정**: `hybrid`가 `dense`보다 나빠졌거나 둘 다 못 찾았는데 다른 문서를 가져온 15번, 권한 밖인데 `hybrid`가 답한 7번을 독립 검수 에이전트 3명이 판정했다. 15번의 다수결은 빈틈 9, 실패 4, 모호 2였다. 사람은 의견이 갈린 것을 정하고, 빈틈 중 판본으로 넣을 것을 골랐다(다수결이 빈틈이어도 판본이 아닌 다른 문서면 넣지 않음).
  - REG(3번)와 Sacrificial Concepts(2번)는 정답 문서의 다른 판본(다른 주의 Weekly Dashboard, #51에서 확정한 CI Product Research Tracker)을 찾은 것이었다. 사람이 판본으로 넣기로 해 평가셋에 더했다.
  - Cannabist와 가향 제품 질문은 판본이 아닌 다른 문서로 답해, #51과 같은 원칙으로 넣지 않았다. "현재 NTM 계획" 질문의 product 부서 실행은 "현재는 최신 문서만 정답" 원칙으로 실패로 봤다.
  - 권한 밖인데 답한 7번 중 2번(Cannabist)은 그 부서가 볼 수 있는 문서에 답이 있는 정당한 답, 5번(Brand Cling 2번, Sacrificial, Crossover Study, 특허)은 단어만 겹치는 청크를 늘려 말한 근거 없는 답이었다.
- **적중 변화** (권한 있는 실행 71번, 실행별 검색 적중률의 합): 나아짐 +9.0(REG 3, Sacrificial 2, Brand Cling, Jezebel, Tobacco 21 각 1, NTM 0.5 × 2), 나빠짐 −2.33(BM25 쪽 청크가 dense 정답을 5위 밖으로 밈 3번). (9.0 − 2.33) ÷ 71 = 0.093. 고유명 실패 9번 중 남은 것은 Cannabist 1번이다.
- **지연 시간** (`dense-53c` → `hybrid-53c`, 중앙값 / p95 ms):

  | 단계 | `dense` | `hybrid` |
  |---|---|---|
  | 질문 임베딩 | 44 / 48 | 43 / 47 |
  | 검색 | 74 / 80 | 85 / 91 |
  | 답변 생성 | 1,514 / 12,249 | 1,976 / 8,321 |
  | 전체 | 1,634 / 12,360 | 2,100 / 8,455 |

  답하는 실행이 늘어 생성 중앙값이 길어졌고, p95가 줄어든 이유는 확인하지 않았다.
- **결정**: 기본값을 `hybrid`로 바꿨다(사람이 결정). 적중률이 크게 오르고 검색 누출률은 0.0이다. 근거 없는 답 5번은 권한 문제가 아니라 답변 품질 문제로 보고 다음 단계에서 다룬다.
- **남은 것**: BM25에서만 잡히는 청크가 늘려 말한 답의 근거가 되는 문제(리랭커, 답변 프롬프트 후보), dense 정답이 밀린 3번(RRF 상수·비중 후보). 상수·비중은 평가셋이 48문항 하나뿐이라 후보 값을 미리 2~3개로 정해 두고 비교한다.
